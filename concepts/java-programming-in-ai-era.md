**结论先说：你的判断大方向可行，但“不会写代码”不能成为目标。更准确的目标是：人负责问题建模、方案选择、约束、验证、风险和上线责任，AI 负责加速实现、补全样板、生成测试和协助排查。**

AI 可以很快写出一个能运行的 Java 服务，但它不会自动知道：业务上的“成功”是什么、数据一致性要到什么程度、一次请求失败后能不能重试、哪一个依赖与现有 BOM 冲突、泄露一个字段是否构成安全事故、或者这段代码在生产流量下是否会把数据库打垮。Java 开发者的核心竞争力因此从“手敲多少代码”转向“能否把系统问题变成可验证的工程约束”。

## 一、先校正对 AI 编程的理解

### 1. 哪些工作可以交给 AI

在需求、接口和约束已经清楚时，以下工作通常适合交给 AI：

- 根据已有项目风格补充 Controller、Service、Repository、DTO 和配置代码；
- 生成 CRUD、序列化、参数校验、日志、异常映射等重复代码；
- 根据明确的行为契约补单元测试、参数化测试和测试数据；
- 将一个小函数重构为更清晰的实现，或把同步调用改成已有的异步抽象；
- 阅读编译错误、测试失败、堆栈和日志，提出可能原因与验证命令；
- 生成 SQL、Dockerfile、CI 配置和文档初稿；
- 在明确的接口和性能目标下比较两三种实现，并产出可运行的实验代码。

### 2. 哪些责任不能外包

以下判断必须由人掌握并签字：

| 责任 | 为什么不能只相信 AI |
| --- | --- |
| 业务规则和边界 | 自然语言中的“有效”“已支付”“可重试”经常有隐含前提 |
| 数据模型与事务 | 错一个唯一约束、隔离级别或更新顺序，可能造成不可逆数据错误 |
| 并发与分布式语义 | AI 容易生成“看起来异步”但实际丢消息、重复消费或死锁的代码 |
| 安全边界 | 认证、授权、租户隔离、敏感字段和密钥不能靠代码表面正确来判断 |
| 依赖与版本 | 生成代码可能引入过时库、传递依赖漏洞或与项目 BOM 冲突 |
| 性能和容量 | 没有真实流量、数据量和资源约束，无法从代码外观推断性能 |
| 生产运维 | 超时、重试、降级、报警、回滚和数据修复都属于系统责任 |
| 验收标准 | 只有业务方和负责系统的人能决定“正确且可上线”是什么 |

一句话：**AI 可以代写实现，但不能替你承担系统的因果关系。**

### 3. 最有价值的能力结构

把 Java 能力拆成六层，比把知识点堆成一张长清单更实用：

1. **读写层**：能读懂 Java、异常、集合、泛型、线程和常见框架代码。
2. **运行层**：知道代码如何编译、装载、执行、分配内存、连接数据库和访问网络。
3. **工程层**：能组织模块、依赖、配置、测试、日志、发布和回滚。
4. **系统层**：能根据一致性、吞吐、延迟、可用性和成本选择方案。
5. **验证层**：能用测试、指标、日志、追踪、压测和故障演练证明方案成立。
6. **协作层**：能把任务拆成 AI 可执行的小步，审查 diff，并控制上下文、风险和变更范围。

## 二、Java 本身必须掌握到什么程度

不需要背完 JDK API，但下面的内容必须能解释、能阅读、能写出小例子，并能识别 AI 生成的错误。

### 1. 语言与对象模型

- 基本类型、引用、装箱拆箱、`null`、不可变对象和 `equals/hashCode` 契约；
- 类、接口、继承、组合、抽象类、默认方法和访问控制；
- 构造器、初始化顺序、方法重载与重写、动态分派；
- 异常层次、受检/非受检异常、异常边界、资源关闭与 `try-with-resources`；
- 泛型的类型参数、通配符、类型擦除，以及为什么不能随意把 `List<Dog>` 当成 `List<Animal>`；
- 注解的保留策略、反射和运行时扫描大致如何工作；
- `record`、`sealed class`、模式匹配、文本块、switch 表达式等现代 Java 语法，重点是读懂项目代码而非追新语法；
- 以接口表达能力、以组合替代不必要的继承，理解对象生命周期和依赖方向。

**最低验证标准：**看到一段带泛型、异常、接口实现和回调的代码，能说清楚它可能返回什么、在哪些路径抛什么异常、对象由谁创建和释放。

### 2. 集合、函数式写法与边界

- `List`、`Set`、`Map`、队列和并发集合的用途、复杂度及是否允许 `null`；
- `ArrayList`、`HashMap`、`TreeMap`、`ConcurrentHashMap` 的基本行为；
- Stream 的 `map/filter/flatMap/reduce/collect`，以及惰性求值、短路、并行流的风险；
- `Optional` 适合表达返回值缺失，不应被滥用于字段、参数和所有空值处理；
- 时间 API：`Instant`、`Duration`、`LocalDate`、时区、序列化格式和数据库时间类型；
- 字符集、字节与字符串、JSON、金额精度和 `BigDecimal`；
- 分页、排序、去重、空集合、重复键和超大输入等边界。

AI 生成的 Stream 代码常常“短但不一定对”：要检查是否改变了顺序、是否重复遍历、是否把异常吞掉、是否在大集合上制造了额外内存峰值。

### 3. 并发、异步与 Java Memory Model

这是 Java 工程中最不能只靠 AI 的部分。

- 线程、进程、锁、竞态条件、可见性、原子性和有序性；
- `synchronized`、`volatile`、`Lock`、原子类、并发集合和线程安全的边界；
- `ExecutorService`、线程池队列、拒绝策略、任务取消和资源关闭；
- `CompletableFuture` 的组合、异常传播、线程池选择和上下文传递；
- 虚拟线程适合大量阻塞 I/O，但不等于 CPU 计算变快，也不能掩盖连接池、锁和下游容量问题；
- 死锁、活锁、饥饿、线程泄漏、阻塞调用混入事件循环；
- 幂等键、重复请求、超时、取消和重试之间的关系；
- “提交异步任务”与“业务已经成功”不是同一件事。

**必须会问的五个问题：**共享状态是什么？谁拥有它？并发上限在哪里？失败如何传播？任务在进程退出时怎么办？

### 4. JVM 运行时与诊断

- JVM、JDK、JRE、字节码、类加载器和 classpath/module path 的关系；
- 堆、栈、元空间、直接内存、线程栈和常见 OOM 类型；
- GC 的目标是权衡吞吐、延迟和内存，不是“垃圾回收越频繁越好”；
- `jstack`、`jmap`、`jcmd`、JFR、GC 日志、线程 dump 和 heap dump 的基本使用场景；
- 类冲突、`NoSuchMethodError`、`ClassNotFoundException`、`OutOfMemoryError` 和连接池耗尽的区别；
- 通过指标和现场证据判断瓶颈，而不是看到一条异常就改代码。

版本策略上，JDK 21 和 JDK 25 都属于 Oracle 列出的 LTS 版本；但项目应首先服从组织支持矩阵、框架兼容性和部署镜像，不要为了追新版本自行升级。Java 语法变化可查 Oracle 的版本说明，运行时行为则要以目标 JDK 的文档和实际测试为准。

## 三、Java 工程底座：AI 写代码前人必须会搭的骨架

### 1. Maven/Gradle 与依赖管理

至少要能独立完成：

- 看懂 `pom.xml` 或 `build.gradle`；
- 区分直接依赖、传递依赖、编译/运行/测试作用域；
- 使用 BOM、统一版本、排除冲突依赖并查看依赖树；
- 理解多模块项目、插件、profile、资源过滤和测试生命周期；
- 让构建在 CI 和新机器上可重复，而不是“我本地能跑”；
- 识别快照版本、动态版本和未经审查的仓库来源；
- 通过锁定版本、依赖扫描和 SBOM 控制供应链风险。

Maven 官方文档把依赖机制、传递依赖、依赖范围和 BOM 都作为核心能力；因此不要只会复制一段依赖声明，要会追踪“最终进了哪个版本”。

### 2. 模块边界与代码组织

推荐从“模块化单体”开始，而不是一上来拆微服务：

- API/Controller：协议适配、鉴权入口、参数校验，不承载核心业务规则；
- Application/Service：用例编排、事务边界、权限和外部调用顺序；
- Domain：业务状态、不变量、领域规则，尽量不依赖 Web 和数据库细节；
- Infrastructure/Repository：数据库、缓存、消息、第三方服务适配；
- Configuration：配置绑定、启动检查、环境差异；
- Test：单元、集成、契约和端到端测试分别说明验证范围。

不要求每个项目机械套 DDD，但必须能说明每一层为什么存在、依赖方向是什么、改变数据库是否会污染 API。

### 3. Spring 生态的必备主干

Spring 不是“会写几个注解”就算掌握。需要理解这些机制：

- IoC 容器、Bean 生命周期、构造器注入、作用域和条件装配；
- Spring Boot 自动配置、配置绑定、profile、启动失败诊断和 Actuator；
- Spring MVC 的请求映射、参数绑定、校验、异常处理和过滤器链；
- WebFlux 的非阻塞模型，以及为什么不能把普通阻塞 JDBC 代码直接塞进事件循环；
- `@Transactional` 的代理边界、自调用失效、传播行为、隔离级别和异常回滚规则；
- Spring Data/JDBC/JPA 的查询、持久化上下文、懒加载、N+1、批量写入和锁；
- Spring Security 的认证、授权、过滤器链、CSRF、会话/JWT/OAuth2 基本边界；
- 配置、日志、健康检查、指标、追踪、优雅停机和外部化密钥。

Spring Framework 6 及以后要求 Java 17+；Spring Boot 的具体最低 JDK、Spring Framework、Maven/Gradle 版本会随 Boot 大版本变化，建立项目时必须查看目标版本的官方兼容矩阵，而不能凭旧教程配置。

## 四、数据、网络与分布式：真正决定方案的知识

### 1. SQL 与关系数据库

这是后端开发的硬底座，即使 AI 能生成 SQL，也不能跳过：

- 表、主键、外键、唯一约束、检查约束和索引；
- B+Tree 索引、联合索引顺序、覆盖索引和回表；
- `EXPLAIN`、慢查询、分页方式和大表变更；
- 事务 ACID、隔离级别、脏读/不可重复读/幻读、锁等待和死锁；
- 乐观锁、悲观锁、唯一约束防重和幂等写入；
- 数据库迁移、向前/向后兼容和回滚策略；
- 读写分离、连接池、超时、重试以及“重试会不会让写入重复”。

**判断标准：**面对一个写接口，你能画出数据表、唯一约束、事务边界、失败回滚方式和并发下的重复请求行为。

### 2. Redis、缓存与状态

- 缓存旁路、读写穿透、击穿、雪崩和热 key；
- TTL、版本号、失效顺序和缓存与数据库的一致性；
- 分布式锁的租约、续期、误删和 fencing token 风险；
- Redis 适合做什么，不适合替代什么；
- session、幂等键、限流计数和短期任务状态的生命周期。

缓存不是“加一个注解就变快”，而是把一致性、失效和容量问题引入系统。

### 3. 消息与异步系统

需要掌握 Kafka、RabbitMQ 或公司消息系统背后的通用语义，而不是死记某个客户端 API：

- producer、broker、partition/queue、consumer group 和 offset/ack；
- 至少一次、至多一次、尽力而为与业务幂等；
- 重复消息、乱序、积压、毒消息、重试队列和死信队列；
- outbox、事务消息、补偿任务和最终一致性；
- 消费者扩缩容、分区数、顺序键和重平衡；
- 消息 schema 演进、兼容性和事件版本。

### 4. HTTP 与服务间通信

- HTTP 方法、状态码、幂等性、缓存头、连接复用和 TLS；
- REST 资源建模、分页、过滤、错误格式、版本兼容和 API 契约；
- JSON 的缺失/null/默认值、金额/时间/枚举的序列化约定；
- connect/read/call timeout、重试预算、退避、熔断、限流和 bulkhead；
- trace/span、request ID、幂等键和跨服务上下文；
- gRPC、WebSocket、SSE、消息队列各自适用的交互形态。

### 5. 一致性与可用性判断

遇到“要不要微服务”“要不要异步”“要不要上缓存”时，先问：

1. 数据的事实来源是什么？
2. 哪些写入必须原子完成？
3. 允许多长时间的不一致？
4. 一次请求最多可以等多久？
5. 下游不可用时是失败、降级、排队还是返回旧数据？
6. 重试、补偿和人工修复由谁负责？
7. 流量、数据量、团队规模和发布频率是否真的支持更复杂的架构？

## 五、场景到方案：先认识问题，再让 AI 选实现

下面的表不是“固定答案”，而是让 AI 和人使用同一套决策语言。

| 场景 | 默认起点 | 需要额外考虑 | 不要盲目选择 |
| --- | --- | --- | --- |
| 普通管理后台/CRUD | 模块化单体 + MVC + 关系库 | 权限、审计、分页、事务、迁移 | 为了“先进”拆微服务 |
| 高并发读 | 数据库索引 + 本地/Redis 缓存 | 一致性、热 key、缓存失效、容量 | 把所有数据都放 Redis |
| 长耗时任务 | 请求入队 + worker + 状态表 | 幂等、进度、重试、取消、死信 | HTTP 请求里同步等待 |
| 跨服务最终一致 | 本地事务 + outbox + 消费者幂等 | 补偿、对账、事件版本 | 仅凭分布式事务注解解决一切 |
| 强一致资金/库存 | 单一事实源 + 明确锁/约束 + 短事务 | 超卖、对账、人工修复、审计 | 先扣缓存再异步落库 |
| 搜索与复杂筛选 | 关系库查询或专用搜索引擎 | 索引延迟、分词、重建、双写 | 把搜索引擎当主数据库 |
| 定时/批处理 | Scheduler + 可恢复 job | 分片、checkpoint、重复执行、并发控制 | 单机内存列表跑全量任务 |
| 文件上传 | 对象存储 + 元数据表 + 异步处理 | 病毒扫描、权限、断点续传、清理 | 文件永久塞进数据库 |
| 实时通知 | SSE/WebSocket 或消息推送 | 连接数、重连、离线补偿、顺序 | 把实时连接当普通 HTTP 请求 |
| 第三方 API 集成 | 防腐层 + timeout + retry + fallback | 限流、签名、幂等、供应商变更 | 在业务代码里散落 SDK 调用 |
| AI/模型调用 | provider adapter + budget + 观测 | prompt 版本、超时、成本、数据脱敏、评测 | 直接把模型响应当可信事实 |
| 高吞吐数据管道 | 消息系统 + 批量处理 + backpressure | 顺序、积压、丢失、回放、schema | 只加线程数解决吞吐 |

**选择原则：**先选满足约束的最简单方案，再用压测、故障演练和真实指标证明是否需要升级复杂度。

## 六、测试、可观测性、安全与交付

### 1. 测试不是让 AI 生成几个 happy path

至少要会区分验证范围：

- 单元测试：纯业务规则、边界和失败分支，运行快；
- 集成测试：真实数据库/Redis/消息系统或尽量接近真实的替身；
- 契约测试：服务间请求、响应、错误和兼容性；
- 端到端测试：关键用户路径，不追求覆盖所有内部实现；
- 性能/负载测试：吞吐、延迟分位数、资源使用、降级和恢复；
- 故障测试：超时、断网、重复消息、数据库只读、依赖返回坏数据。

测试应描述行为而不是锁死实现细节。AI 生成的测试尤其要检查：断言是否真的能失败、是否只验证 mock 被调用、是否遗漏并发和重试路径。

### 2. 可观测性

生产系统至少应有：

- 结构化日志：请求 ID、业务主键、错误分类，避免密码和 token；
- Metrics：吞吐、错误率、延迟分位数、队列积压、连接池、GC 和资源水位；
- Traces：跨服务调用、数据库、消息消费和外部 API；
- Health/readiness/liveness：区分“进程活着”和“能接收流量”；
- Dashboard、报警阈值、runbook 和一次可复现的排障路径；
- 发布版本、配置版本和数据库迁移版本的关联。

没有可观测性，就无法验证 AI 生成的系统是否真的工作，也无法在事故中区分代码错误、容量不足和下游故障。

### 3. 安全底座

- 认证（你是谁）和授权（你能做什么）分开；
- 租户/用户边界在查询、缓存、消息和日志中都要保持；
- 参数校验、SQL 参数化、输出编码、文件路径和 SSRF 防护；
- 密钥使用环境变量/密钥管理系统，不能写进代码、日志或 prompt；
- 依赖漏洞、镜像漏洞、许可证和供应链来源；
- 密感数据分级、脱敏、加密、保留周期和审计；
- 限流、资源配额和请求体大小，防止“合法请求”拖垮系统；
- 参照 OWASP Top 10 做威胁建模和上线前检查，而不是只等扫描器报警。

### 4. 交付与运行

- Git 分支、提交、代码审查和小步回滚；
- CI：编译、静态检查、单测、集成测、依赖扫描、制品构建；
- Docker 镜像、非 root 用户、健康检查、优雅停机和资源限制；
- 配置与密钥分离，dev/staging/prod 不靠手工改文件；
- 数据库迁移的 expand/contract 策略；
- 灰度、金丝雀、feature flag、回滚和数据修复；
- Kubernetes 等平台只在确有调度、弹性和隔离需求时引入，不把平台复杂度误认为工程能力。

## 七、AI 协作开发的正确工作流

### 1. 先给 AI “可执行的上下文包”

不要只说“帮我写一个订单服务”。至少提供：

```text
背景：这是一个 Java/Spring Boot 模块化单体，使用 PostgreSQL 和 Redis。
目标：新增“创建订单”用例。
业务规则：同一幂等键只能成功一次；库存不足返回明确错误；订单和扣库存必须在同一事实边界内。
接口：POST /orders，请求/响应 JSON 结构如下……
约束：遵循现有包结构和异常格式；不能引入新依赖；金额使用 BigDecimal。
失败语义：数据库冲突、库存不足、下游超时分别如何返回。
验收：列出测试场景，包含重复请求、并发扣库存、事务回滚和非法参数。
交付：先给设计和改动文件列表，确认后再逐文件实现。
```

### 2. 让 AI 先读项目，再动手

推荐顺序：

1. 让 AI 列出项目结构、入口、构建命令、测试命令和相关模块；
2. 指定它阅读相似用例、数据库迁移、异常处理和测试；
3. 让它复述现有约定，并指出不确定的地方；
4. 先产出方案、接口契约和变更清单；
5. 按一个行为或一个小模块实现；
6. 立即运行格式检查、编译和最小测试；
7. 检查 diff、依赖、日志和错误路径后再进入下一步。

“先探索、再计划、后修改”比一次性让 AI 生成整套系统更容易控制。

### 3. 每次让 AI 交付可验证的结果

每个任务都要求 AI 同时给出：

- 修改了哪些文件以及为什么；
- 新增了哪些行为和不支持哪些行为；
- 使用了哪些依赖、配置和外部服务；
- 如何运行编译、单测、集成测和压测；
- 已知风险、假设和需要人工确认的点；
- 如果失败，如何回滚或清理数据。

### 4. 人工审查的五层顺序

1. **契约层**：接口、状态码、事件、数据库字段是否符合业务约定？
2. **数据层**：事务、唯一约束、隔离级别、迁移和并发是否成立？
3. **失败层**：超时、重试、取消、重复、乱序、部分成功怎么处理？
4. **安全层**：权限、租户、注入、敏感数据和依赖风险是否清楚？
5. **运行层**：日志、指标、追踪、容量、报警和回滚是否可用？

只有这五层通过，才值得讨论代码是否“优雅”。

### 5. 适合 AI 的任务切分

适合：

- “为 `OrderPolicy` 补充 8 个边界测试”；
- “按现有异常格式把数据库唯一冲突映射为 409，并说明测试”；
- “阅读这三个模块，列出事务边界和可能的 N+1”；
- “不改变公开 API，把这个循环重构为可测的策略对象”；
- “为这个消息消费者增加幂等表，先给 schema、状态机和失败语义”。

不适合：

- “从零设计一个高并发订单平台并直接生成全部代码”；
- “把同步系统改成微服务，保证不出问题”；
- “优化性能”但不给流量、数据规模、基线和目标；
- “修复所有安全问题”但不提供威胁模型和扫描结果。

## 八、学习路线：不死磕 API，但要形成可验证能力

### 阶段 0：建立工具闭环（1 周）

目标：能让项目稳定地跑起来。

- 安装并切换 JDK，理解 `JAVA_HOME`、classpath 和 `java -version`；
- 会用 IntelliJ IDEA 或 VS Code 调试断点、查看变量和调用栈；
- 会执行 Maven/Gradle 的编译、测试、打包和依赖树；
- 会读 Git diff、提交、回滚和最小化变更；
- 让 AI 先生成项目地图和运行说明，自己逐条验证。

产出：一个能在新机器或容器中一条命令启动、另一条命令测试的最小服务。

### 阶段 1：Java 语言与 JVM（2–3 周）

重点：对象模型、集合、泛型、异常、IO、并发和 JVM 诊断。

练习：用标准 JDK 写一个带限流、超时、优雅关闭和持久化文件的任务队列；故意制造线程安全错误，再用测试和线程 dump 定位。

通过标准：能解释一段 AI 生成的并发代码为什么安全或不安全，而不是只看它能否编译。

### 阶段 2：Spring Boot + SQL（3–4 周）

重点：MVC、DI、事务、校验、异常、数据库迁移、索引和测试。

练习：做一个订单/库存模块，包含幂等创建、库存并发扣减、分页查询、审计和集成测试。让 AI 生成样板，人负责数据模型和测试矩阵。

通过标准：能从请求一路追到事务、SQL、提交结果和错误响应。

### 阶段 3：缓存、消息与可观测性（2–3 周）

重点：Redis、消息消费、幂等、重试、死信、日志、指标和追踪。

练习：把订单支付通知改为异步事件，加入 outbox、重复消费、重试和对账任务；用 Docker 启动依赖，写出故障测试。

通过标准：能画出成功、超时、重复、乱序和恢复路径。

### 阶段 4：架构与生产化（持续）

重点：模块边界、容量估算、部署、灰度、回滚、故障排查和安全。

练习：为前面的系统写一份 ADR，明确为什么暂时保持模块化单体、什么时候拆分、指标是什么、拆分后增加哪些一致性成本。

通过标准：能拒绝不必要的复杂架构，也能说明何时复杂度已经值得。

### 阶段 5：AI 协作能力（贯穿全程）

建立个人提示词和审查模板库：项目探索、设计评审、代码实现、测试生成、故障分析、安全审查和发布检查各一套。重点不是“会不会写 prompt”，而是能否提供准确上下文并验证结果。

## 九、建议的最小实践栈

不要同时学习十套框架。可以先固定一条主线：

- JDK：以组织支持的 LTS 为准；新项目在 Java 21/25 之间按 Spring Boot、基础镜像和依赖兼容性选择；
- 构建：Maven 或 Gradle 选一个深学，另一个能读；
- Web：Spring Boot + Spring MVC；理解 WebFlux，但不要为了简历强行使用；
- 数据：PostgreSQL 或 MySQL + Flyway/Liquibase；
- 缓存：Redis；
- 消息：Kafka 或 RabbitMQ 选一个，重点学投递语义和故障处理；
- 测试：JUnit 5 + Mockito，集成测试使用真实容器或 Testcontainers 思路；
- 运行：Docker、Linux、CI、基础 Kubernetes 概念；
- 观测：结构化日志、Micrometer/Prometheus、OpenTelemetry；
- 安全：Spring Security、OWASP Top 10、依赖和镜像扫描。

这套栈的目的不是覆盖所有 Java 工作，而是让你能独立完成一条从需求、代码、数据、测试到上线的闭环。

## 十、AI 编程时代的个人验收清单

接手一个 Java 项目或 AI 生成的改动时，逐项回答：

### 我是否理解它

- 我能画出请求/消息的完整路径吗？
- 我知道每个数据字段的来源、事实归属和生命周期吗？
- 我能说清线程、事务、连接池和消息消费者的边界吗？
- 我知道哪些行为是约定，哪些只是当前实现吗？

### 我是否能验证它

- 有正常、边界、重复、并发、超时和恢复测试吗？
- 测试断言的是业务行为，而不是 mock 的表面调用吗？
- 有编译、静态检查、依赖扫描和集成测试吗？
- 有基线、压测方法和资源指标吗？

### 我是否敢让它上线

- 认证授权和敏感数据处理经过审查了吗？
- 失败时会不会重复扣款、丢消息、污染缓存或产生孤儿数据？
- 有日志、指标、追踪、报警、runbook 和回滚方案吗？
- 数据库迁移能否向前兼容，失败后能否修复？
- 我能在不依赖 AI 的情况下解释这次变更的风险吗？

如果最后一个问题答不上来，说明还没有真正掌握这次改动。

## 十一、最终判断：你的想法可行，但要把“编程能力”重新定义

你的方向适合现在的开发环境：不必把时间主要花在记忆样板代码、手写 getter/setter 或从零搭脚手架上；这些工作可以让 AI 加速。但以下能力不能省略：

1. **抽象能力**：把模糊需求变成实体、状态、约束、接口和验收标准；
2. **机制理解**：知道 Java、JVM、事务、线程、网络和数据库在运行时发生什么；
3. **方案判断**：能在单体/微服务、同步/异步、缓存/数据库、强一致/最终一致之间做取舍；
4. **验证能力**：用测试、日志、指标、压测和故障演练证明 AI 的代码没有越过边界；
5. **责任意识**：安全、数据、成本、可用性和回滚不能由“AI 说可以”来背书。

因此，目标不是“会不会写 Java”，而是：**给你一个 Java 系统问题，你能否快速建立模型、选择合理方案、让 AI 生成可控的实现，并用证据证明它在真实约束下成立。**

这是一种更高阶的编程能力，而不是编程能力的消失。
