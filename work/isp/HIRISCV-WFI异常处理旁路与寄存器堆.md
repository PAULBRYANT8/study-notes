# HIRISCV：WFI、异常地址、bypass、stall 与寄存器堆

WFI 是提示硬件可以等待中断的指令；异常处理要区分“导致异常的指令地址”和“出错的目标地址”；bypass 与 stall 则分别通过转发数据和等待数据处理流水线依赖。

本文结合本机 `/home/zhangwei/文档/monalisa/hiriscv/ifu.v`（取指单元 IFU）和 `idu.v`（译码单元 IDU）阅读。行号以当前文件为准；只有这两个片段，缺少 ALU、访存、寄存器堆、顶层与完整测试，因此信号的上游产生方式、系统唤醒机制和端到端正确性不能仅凭它们确定。下面先解释 RISC-V 的标准语义，再讨论这份代码的设计意图；不能把自定义信号直接当成标准 CSR。

## 1. WFI 是什么

### 1.1 作用与常见用法

WFI（Wait For Interrupt，等待中断）告诉硬件：当前硬件线程（hart）暂时没有其他工作，可以停下来等待可能需要处理的中断，以便实现有机会降低功耗。例如系统没有任务可运行时，空闲循环可以检查任务或中断状态，然后执行 WFI；有可处理事件后，再检查状态并继续工作。

它是**给硬件的提示**，不保证一定进入低功耗状态，也不保证执行后一定睡眠到中断到来：规范允许实现把 WFI 当作 NOP；硬件也可以在没有实际进入中断处理程序的情况下恢复执行。因此软件不能只凭 WFI 返回就假定某个特定事件已经发生，通常需要再次检查状态，没有可处理的事件时继续等待。WFI 也不是内存屏障，不能代替同步原语或内存顺序约束。[来源：RISC-V 特权架构，Wait for Interrupt](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)

需要区分两个动作：

- **唤醒 / 恢复执行**：硬件停止等待，准备继续运行。
- **真正接受中断并进入 trap handler**：根据中断待处理状态、使能与特权级等条件触发陷入，保存上下文并跳转到处理程序。

这两者不完全相同。规范要求 WFI 对各特权级**局部使能且待处理**的中断恢复，即使相应的全局中断使能关闭；中断委托设置不影响 WFI 的操作。是否真的进入中断处理还要看正常的中断接受条件。WFI 可以在所有特权模式使用，也可选支持 U 模式；特权配置等条件还可能使其产生非法指令异常。

假设 WFI 指令位于 `0x100`：如果等待期间产生并接受了符合条件的中断，处理程序中的 `mepc` 指向下一条指令 `0x104`；若唤醒但未接受中断，则从 `0x104` 继续执行并由软件检查事件。这里说的是**WFI 正常执行后的中断或恢复**，不适用于 WFI 自己触发非法指令等同步异常的情形。WFI 是 32 位指令，因此这里加 4。

### 1.2 这两份代码如何处理 WFI

1. `idu.v:174–177` 比较完整的 32 位指令编码，检测到有效的 WFI 且没有 redirect 时拉高 `idu2ifu_wfi_flag`。它不会像普通运算指令那样通过 `idu_valid` 发往 ALU（见 `idu.v:103–104`）。
2. `idu.v:240–241` 用 `stall_wfi` 检查 `idu2alu_valid`、`alu2meu_rd_valid` 和 `rf_wvalid`，意图是等待较早的流水线工作排空。信号名暗示它们对应各级有效工作或写回，但仅凭本文件不能证明覆盖了所有可能的副作用，例如是否包含每一种尚未完成的 store。
3. `ifu.v:112–123` 用 `wfi_flag_v` 暂存检测结果，并在这三个有效信号都为 0 时产生 `wfi_retire`。这里的 `retire` 是代码自定义的“认为 WFI 可以结束并进入等待”的信号名，不能仅凭名字证明满足完整的架构级退休要求。
4. `ifu.v:74–87、101–107、125` 在 `wfi_retire` 时把 `core_status` 置为 `2'b11`，通过 `core_status[0]` 抑制后续有效取指输出，并把 `wfi_retire` 纳入 `flush_flag`。从状态赋值和门控方式看，这表示设计试图进入停止取指的状态；没有状态枚举定义可进一步证明完整状态机。
5. IFU 中看不到中断输入；可见的 `start_pulse_sync` 会将状态置为 `2'b00`，并以 `start_pc_sync` 作为启动地址。它是否承担中断唤醒、谁提供正确的恢复 PC，需要查看顶层和其他模块，不能断言已经实现标准 WFI 中断唤醒。

**阅读时需留意**：`ifu.v:43` 写成 `reg wfi_flag v;`，不是合法的单个标识符；后文使用的是 `wfi_flag_v`。即使按后者理解，它在这份代码里只在复位时清零、置位后没有清除路径，因此会反复参与 `wfi_retire`，可能妨碍后续启动。`ifu.v:128` 还有多余的右括号，`ifu.v:151、156` 的 `# DLV`、`idu.v:246、249` 的 `#'DLY` 也与其他地方的 ``#`DLY`` 不一致，需结合宏和工程编译环境检查。`idu.v:81` 的 `wire idu2ifu stall;` 同样不像合法的预期信号声明。这些是当前片段中的问题或疑点，不能把它们当作已验证可运行的完整实现。

## 2. 异常为什么要记录指令地址

### 2.1 先分清几种地址

以 RISC-V 机器模式陷入为例，以下是不同用途的地址：

- **异常 PC（`mepc`）**：同步异常发生时通常指向遇到异常的指令；中断则记录被中断的指令地址。处理程序依此定位指令，并按异常原因决定重试、修改返回位置或终止。
- **出错地址**：例如未对齐的跳转目标或 load 的访问地址。`mtval` 在某些异常中可以提供相关的出错虚拟地址，但规范允许具体平台在相应情况下写零，不能假定一定提供有效地址；非法指令异常时也可能提供指令位模式。
- **处理程序入口地址**：由陷入向量机制决定，告诉处理器去哪里运行处理程序；它不是故障指令地址，也不是故障目标地址。

`mepc`、`mtval` 和 `mcause` 各回答不同问题：在哪里发生、附加故障信息是什么、发生了什么。它们不能互相替代。其他特权级有对应的陷入寄存器。[来源：RISC-V 机器级架构，mepc、mcause、mtval](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)

### 2.2 跳转目标未对齐：记录跳转指令，而不是仅记录目标

假设只支持 4 字节对齐的指令地址（`IALIGN=32`）：

```text
0x100: jal x1, +6       # 目标是 0x106，不满足 4 字节对齐
```

这条跳转本身导致指令地址未对齐异常。规范将异常归属于 `0x100` 的跳转指令，进入 M 模式处理时 `mepc = 0x100`；若平台为该异常提供有信息的 `mtval`，它可记录出错目标 `0x106`。条件分支只有在**实际跳转**且目标未对齐时才会因此异常，未跳转不产生这个异常。若实现支持 `IALIGN=16`，对齐要求不同，不能机械套用 4 字节规则。[来源：RISC-V RV32I 基础指令集](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html)

为什么需要 `0x100`？它能唯一指出是哪条指令做出了这次控制流转移，供处理程序和调试器检查指令、操作数和上下文，决定是否修复状态后重试或报告错误。仅有 `0x106` 不能可靠地反推出是哪条分支或跳转造成的：不同位置的多条指令可能跳向同一个目标，目标处也未必存在可执行指令。再者，`mepc` 的作用是给处理程序提供异常指令 / 恢复位置；把未对齐目标塞进只接受有效对齐 PC 的 `mepc` 也无法表达预期含义。规范还指出，在 `IALIGN=32` 的系统上把未对齐异常归属于分支或跳转有助于调试并简化硬件。

这不意味着**所有**与跳转目标有关的异常都归属于跳转指令：若跳转目标对齐，但对目标指令取指时发生 instruction access fault 或 instruction page fault，异常归属于**目标指令**。load/store 地址异常则归属于访问内存的 load/store 指令；出错的数据地址是另一项信息。中断是异步事件，也不应笼统说成“某条指令引发了中断”。

### 2.3 对应到 IFU / IDU

- `ifu.v:49–52`：`redirect_pc_excep` 检查 `alu2ifu_redirect` 有效且目标地址 `alu2ifu_redirect_pc[1:0]` 非零；发生此类异常时，`pc_excep_pc` 选择 `alu2ifu_excep_pc`，而非目标地址。**根据命名和用途推测**，上游希望用它传入触发 redirect 的指令 PC，但这里没有 ALU 源码，无法证明该信号实际值。
- 启动地址异常走另一分支：`start_pc_excep` 成立时选择 `start_pc_sync`。这是外部启动地址检查，没有可由这两个片段确认的跳转指令 PC，应单独理解，不要混同于标准跳转未对齐异常。
- `ifu.v:64–70` 寄存所选异常地址；`idu.v:151–160` 在非法指令条件下保存 `ifu2idu_pc`，在 PC 异常条件下保存 `ifu2idu_pc_excep_pc`。`core_exceptions_pc` 是本设计的输出，不能直接断言它是标准 `mepc`；代码中也没有看到用于记录未对齐目标的 `mtval`。
- `ifu.v:49–52` 的启动地址未对齐检查没有被 `start_pulse_sync` 限定，而是参与每次 `ifu_valid` 下的 `pc_excep`，且在选择地址时优先于 redirect 异常。因此如果启动地址持续未对齐，可能影响后续异常判定；是否被系统输入约束消除需看顶层。`idu.v:138–160` 中异常类型寄存器优先处理 `pc_exception`，异常地址寄存器却优先处理 `ins_exception`；二者同时有效时可能出现类型与地址不匹配，是否可能同时有效需要结合时序验证。

## 3. bypass 与 stall

### 3.1 为什么会出现数据冒险

流水线将多条指令重叠执行。后面的指令可能已经要读操作数，而前面的指令虽然逻辑上先执行，却还没有把最新结果写入寄存器堆。这叫**读后写数据依赖**（RAW，Read After Write）：后面的读必须看到前面那次写的正确结果，直接读取寄存器堆可能得到旧值。

```asm
add x5, x1, x2     # 假设结果为 12，尚未写回 x5
add x6, x5, x3     # 下一条需要的是新值 12，而不是 x5 的旧值
```

如果完全不处理，第二条指令就可能算错。实现可以等待写回后再读，但会降低吞吐量；也可以在结果已经产生但还没写回时，将它提前送给需要它的指令，这就是 bypass（旁路，也常称 forwarding，转发）。

### 3.2 bypass 的本质与核心

bypass 是一条**从较早指令的结果产生位置到较晚指令的操作数输入位置的数据通路**，配合选择逻辑，让消费者不用等结果先写入寄存器堆再读出。它不取消最终写回，不消除程序的数据依赖，也不能凭空生成尚未就绪的值。可以把它理解成“结果已经算好，就先从中途交给后面的指令”。

核心是同时做对以下几件事：

1. **判断依赖**：消费者确实使用该源寄存器；把其 `rs1` 或 `rs2` 与流水线中有效生产者的目的寄存器 `rd` 比较。无效写入和对 `x0` 的写入不能当作普通生产者。
2. **确认值已就绪**：匹配只说明有依赖，并不说明这个阶段已经有最终值；例如 load 在地址算出后仍可能在等内存数据。
3. **选择正确生产者**：若多条更早指令都写同一个寄存器，要选择程序顺序上距离消费者最近、且确实有效的那一条。不能绕过一个尚未就绪的较新生产者去使用更旧的值。
4. **选择数据**：用多路选择器在可用的旁路结果和寄存器堆读数之间选择；没有可用的新值时由控制逻辑阻塞等待。

例如连续执行 `add x5, x1, x2`、`add x5, x3, x4`、`add x6, x5, x7` 时，第三条应使用第二条写 `x5` 的结果，不能使用第一条的旧结果。

### 3.3 stall 是什么，与 bypass 有什么不同

stall（停顿）是控制逻辑暂缓某条指令或某些流水级推进，直到条件满足；实现通常保持受阻指令和相关状态，同时向下游注入无效周期（bubble，气泡），但具体哪些级保持或继续排空取决于设计。stall 可用于等待数据、内存、结构资源或其他控制事件，不只用于 RAW 冒险。

| 问题 | bypass | stall |
|---|---|---|
| 手段 | 把已产生且可用的新值直接送给消费者 | 让消费者等待条件满足 |
| 数据尚未产生时 | 不能提供正确结果 | 可以等待生产者或内存 |
| 对推进的影响 | 在时序允许时减少不必要的等待 | 引入一个或多个等待周期 |
| 硬件重点 | 地址比较、有效位、优先级和数据选择 | 冒险检测、握手、保持状态和插入气泡 |

两者经常配合。例如 `lw x5, 0(x1)` 后紧跟 `add x6, x5, x3`：load 前面阶段可能只有地址，还没有从内存读出的数据。此时不能把地址当成 `x5` 的值，消费者需要 stall；等读出结果可用后，再从某级旁路转发，或等待写回后读取。需要停几拍由实际流水级、存储器延迟和旁路路径决定，不能一概而论。

### 3.4 这份 `idu.v` 的路径

- `idu.v:194–196` 从指令字段提取 `rs1`、`rs2`、`rd`；`223–226` 结合译码结果标记指令实际使用哪些源寄存器、普通目的寄存器和 load 目的寄存器。这里的指令子集是该代码的选择，不是完整 RV32I。
- `idu.v:243–285` 分别为两个源操作数检查 3、4、5 级的目的地址与对应有效条件。`rs1/rs2` 为零时直接返回 0；否则依次选择 3 级、4 级、5 级数据，最后才使用寄存器堆读数据 `rdata_rs1/rdata_rs2`。当这几级确实依程序顺序由新到旧时，这个优先级体现了选择最近生产者的意图；各级信号是否始终与对应指令对齐，要看缺失的上下游。
- `idu.v:228–239` 对 load 的目的地址与消费者源地址比较：3 级使用延迟后的 `ins_rd_stall_related_d`，4 级使用 `alu2meu_lw_flag`；匹配时产生 `stall_rs1/rs2`。这说明设计意图是等 load 的结果可用；具体时序和停顿周期数不能单凭片段推定。
- `idu.v:103–118、240–241` 中，stall 使 `idu_valid` 为 0，避免受阻指令继续作为有效指令进入下一级；`idu2ifu_ready` 通常变低以施加反压，但 redirect 时优先允许处理控制流变化。IFU 部分寄存器仅在 ready 时更新（`ifu.v:144–156`）；完整握手是否保持所有必需信息仍需仿真验证。
- **潜在多余停顿**：`stall_rs1/rs2` 的地址比较没有排除 `rd == x0`。例如 `lw x0, 0(x1)` 后消费者读取 `x0`，表达式可能错误地判定数据相关并停顿；`x0` 恒为零，load 自身的内存访问和异常仍需保留，只是没有寄存器值依赖。是否实际触发还取决于上游地址 / 有效信号。

## 4. 寄存器与寄存器堆的区别

**寄存器**是保存一组二进制状态的存储单元；例如一个 32 位寄存器可保存一个 32 位值。硬件中有很多用途不同的寄存器：程序计数器 PC、流水级之间保存指令和控制信息的寄存器、状态 / 控制寄存器，以及程序可读写的通用寄存器。Verilog 中的 `reg` 是一种变量声明类型，并不自动等同于“CPU 通用寄存器”：综合成触发器、锁存器还是组合逻辑要看赋值方式和是否完整赋值。

**寄存器堆**（register file，RF）是组织为一组可按编号访问的寄存器及其读写接口的硬件结构。把单个寄存器想成一个有固定宽度的格子，寄存器堆就是许多格子加上“按编号选择并读写”的电路。它可以用触发器、多路选择器、存储器宏等方式实现；物理实现并不要求每个架构寄存器都对应一个独立可见的触发器组。

以标准 RV32I 的整数架构状态为例，有 `x0`–`x31` 共 32 个 32 位整数寄存器，`x0` 恒为 0；PC 是另外的架构状态，不能简单等同于整数寄存器堆中的一个普通条目。不同 ISA、扩展及实现的数量和宽度可以不同。[来源：RISC-V RV32I 程序员模型](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html)

一条 `add x5, x1, x2` 通常需要按编号读出 `x1`、`x2`，运算后把结果写入 `x5`。一个常见设计为此提供两个读端口和一个写端口，但端口数量、读写延迟、同周期读写同一地址时的行为都属于具体设计，不是所有寄存器堆的固定属性。同周期读写是否能直接读到新值，也可能影响是否需要写回级旁路。

在这份代码中：

- `idu.v:35–39、194–195` 的 `rs1`、`rs2` 是送到外部寄存器堆的 5 位读地址，`rdata_rs1`、`rdata_rs2` 是返回的 32 位读数据；寄存器堆模块本身未提供，不能从这两个文件确认它的内部实现或读写时序。
- `idu.v:120–135` 的 `idu2alu_rd_addr`、`idu2alu_pc`、`idu2alu_inst_sel` 在时钟沿保存信息，是译码到执行的流水线寄存器；它们不是按 `x0`–`x31` 编号访问的整数寄存器堆。`ifu.v` 中的 `pc_nd`、`core_status` 也是各自用途的状态寄存器。
- `data_rs1_bypass`、`data_rs2_bypass` 虽声明为 `reg`，却在 `always @(*)` 中被完整选择赋值，表达的是组合选择结果；不应仅凭 `reg` 关键字就说它们各自是时钟触发的存储寄存器。
